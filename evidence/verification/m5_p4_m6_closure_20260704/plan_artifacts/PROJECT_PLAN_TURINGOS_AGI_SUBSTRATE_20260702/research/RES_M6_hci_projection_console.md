### 2.4 Projection-integrity audit: patterns and design

**WEB** — established event-sourcing/CQRS practice maps cleanly onto MicroTape:
- Read models must be **rebuildable from scratch** from the event stream, which is the sole source of truth; never store anything in a read model that cannot be reconstructed ([Event-Driven.io — Guide to Projections and Read Models](https://event-driven.io/en/projections_and_read_models_in_event_driven_architecture/), [Azure Architecture Center — Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)).
- **Shadow projections / blue-green rebuilds**: build the same projection a second time from the stream and validate it against the serving copy before cutover ([Ashraf Mageed — CQRS, Event Sourcing, and the Cost of Tooling Constraints](https://www.ashrafmageed.com/cqrs-eventsourcing-and-the-cost-of-tooling-constraints/)). The console's `snapshot_hash` (JCS-canonical sha256 over every displayed field, `lib.rs:303–319`) makes shadow-comparison a one-line equality check.
- Determinism preconditions (schema governance, versioned projections, idempotent application) are already satisfied structurally here: the tape is an append-only git DAG, `projection_version` is a schema field, and rebuilds are cold-start pure functions — MicroTape avoids the checkpoint/duplicate-delivery machinery entirely because reads are not consumers of a broker.

**REASONED** — the audit must check **four distinct properties**, because hash-equality alone has a blind spot (two runs of the same buggy builder agree with each other):
1. **Rebuild determinism (shadow projection):** build `operator_view_snapshot.v1` twice — once from the live tape path, once from a fresh `git clone`/bundle of the same tape — and assert byte-identical JCS preimages (`snapshot_hash` equality). Catches: hidden host state, wall-clock leakage, nondeterministic ordering.
2. **Independent head derivation:** recompute `tape_tip`/`authorization_head`/`accepted_head` with an *independent reference reader* (Python, in the style of `audit_micro_tape_decision_dag.py`, reading refs and event bodies directly via `git rev-parse`/`cat-file` — never importing `turing-projection`) and assert they equal the snapshot's `heads`. Catches: a builder that displays fabricated or stale heads deterministically.
3. **Field provenance closure:** every leaf field in the rendered snapshot must be classified in a checked-in **provenance manifest** (JSON pointer → one of `tape_ref`, `tape_event_body`, `derived(<named pure function>)`, `schema_constant`, `command_spec_constant`). The audit walks the snapshot; any unclassified field = FAIL. This mechanizes "100% of console-displayed values replayable from tape" (G7) instead of trusting a human to notice a new field. New fields therefore *cannot ship without declaring their tape derivation*.
4. **Render fidelity:** the human-text renderers (`status` heartbeat, `panoview`) may format but not derive (the contract in `docs/hci/OPERATOR_AGENT_CONTRACT.md`: "Renderers may format fields. They may not derive new truth, hide warnings, or change severity order"). Check: parse the text output, and assert every value token in it appears verbatim in the snapshot JSON (the existing `audit_operator_cli_copy.py` is the seed of this; extend it from copy-law words to value tokens).

### 2.5 No-write proof for the Rust crate: static candidates and their blind spots

1. **Dependency-direction check (strongest, already true, keep it true).** **ON-DISK**: `turing-projection` has no `turing-git-tape` dependency — the writer type is unreachable. Gate: a CI step running `cargo metadata` and failing if `turing-projection`'s (transitive) dependency set ever includes `turing-git-tape` or any crate exporting an append capability. Pros: unforgeable at the type level; zero annotations. Cons: does not cover `turing-cli`, which legitimately needs tape reads and *does* import `Append`.
2. **Capability split: introduce a read-only handle type.** **REASONED**, grounded in the existing API shape: add `TapeReader` to `turing-git-tape` exposing only `open`, `head_set`, `head_set_guarded`, `committed_body_bytes`, `commit_parents` (all already exist, `append.rs:392/409/436/885/891`) and make the operator paths take `TapeReader`, never `Append`. Then "the console cannot write" becomes a *visibility/type* fact: the write capability is simply not in scope. Pros: the classic capability-security move; survives refactors; self-documenting. Cons: small upstream crate change (M1 owns that crate's roadmap — coordinate, don't fork).
3. **Clippy `disallowed-methods` / `disallowed-types`.** **WEB**: clippy supports a `clippy.toml` with `disallowed-methods`/`disallowed-types` entries as fully-qualified paths with optional `reason` and `replacement`; warn-by-default but only fires when configured; enforce as a hard error via `-D warnings` or `#![deny(clippy::disallowed_methods)]` ([Clippy lint configuration](https://doc.rust-lang.org/clippy/lint_configuration.html), [Clippy configuration guide](https://doc.rust-lang.org/clippy/configuration.html), worked example at [schneems.com](https://www.schneems.com/2025/11/19/find-accidental-code-usage-with-a-custom-clippytoml/)). **Known blind spots (must be stated in the gate doc):** it cannot detect higher-order uses (passing `Append::append` as a function value) ([rust-clippy issue #8849](https://github.com/rust-lang/rust-clippy/issues/8849)), and any site can be `#[allow(clippy::disallowed_methods)]`-ed — so the grep gate must also grep for the allow-attribute itself.
4. **Self-testing grep gate (house style).** Port the `gate_g10_provenance.sh` pattern: ban, in `crates/turing-projection/**` and the operator modules of `turing-cli`, the strings `.append(`, `.stage(`, `AppendRequest`, `re_mint_and_commit`, `update_ref`, `refs/turingos/` (write context), `std::process::Command` (except the whitelisted `run_git` read helper), and `#[allow(clippy::disallowed_` — with `--self-test` fixtures proving both directions. Pros: catches what clippy structurally cannot; auditable in one screen; NOT_RUN≠PASS exit discipline. Cons: string-level, needs a curated whitelist (e.g., `BundleScratch`'s `create_dir`/`remove_dir_all` on a temp path).
5. **Dynamic head-conservation test.** Port `test_panorama.py`'s conservation assertion to Rust: for a fixture tape, capture the three ref OIDs, run *every* console command (status/panoview/explain/ask/operator stdin script/approval preview) against it, re-read the refs, assert byte-identical. **ON-DISK gap**: the current `cli_gates.rs` additions assert heads are *displayed* correctly but never assert they are *conserved* — this test does not exist yet and is required by the G7 KPI ("dynamic test").
6. **Read-only filesystem hardening test (cheap, brutal, recommended).** Run the full console command matrix against a fixture tape whose directory tree has been `chmod -R a-w`-ed (and, in CI, a read-only bind mount): every read command must still succeed; any latent write path fails loudly with EACCES instead of silently mutating. **REASONED**: this converts "we found no write path" into "no write path can physically execute", covering even unsafe/higher-order blind spots of items 3–4.

### 2.6 Presentation stack: plain CLI vs TUI vs web

- **Plain CLI (current, verified §2.1-D).** **WEB**: the [CLI Guidelines](https://clig.dev/) case — machine-readable stdout, pipe-composability, stateless deterministic output — is exactly the property set an *audit* console needs, and plain stdout is trivially testable (run binary, assert on text), which is how all 16 existing `cli_gates.rs` tests already work. CLI output is also the cheapest surface for the projection-integrity audit to parse, and the friendliest to the agent fleet (agents consume text, not pixels).
- **Ratatui TUI.** **WEB**: testable via `TestBackend` + insta snapshots ([Ratatui — Testing with insta snapshots](https://ratatui.rs/recipes/testing/snapshots/)), but snapshot tests are brittle, color assertions unsupported, PTY behavior untestable without extra harnesses, and immediate-mode UIs move state management (scroll, selection) into the console — new derived state the copy-law lint and render-fidelity audit cannot easily see. **REASONED**: defer; nothing in G7 needs it; the `textual`-optional pattern in `panorama.py` shows the house already treats rich UI as an optional layer over a text contract.
- **Web console.** **REASONED**: rejected for this increment — it adds an auth/secret surface (violates NFR §6 "no secrets on tape"/custody discipline by creating a new credential store), a served mutable endpoint (drift gravity toward HCI-C, which is forbidden), and the heaviest audit burden for zero G7 benefit for a single operator on one VM.
- **Recommended enhancement (small):** add `--json` to `status`/`panoview` that prints the `operator_view_snapshot.v1` JSON verbatim. Then "what the UI displays" and "what the schema validates" are the *same bytes*, and audit property 4 (§2.4) becomes near-trivial for the JSON mode.

### 2.7 Zone separation: mapping the four constitutional zones onto existing constructs

**ON-DISK** — all four zones already have on-disk anchors; the ADR should bind them explicitly:
1. **Projection**: `operator_view_snapshot.v1` with `source_kind ∈ {guarded_micro_tape_read, deterministic_replay}`, `can_write_truth: const false`, `snapshot_hash`.
2. **Intent-preview**: `typed_command.v1` (`dry_run_default: true`, `writes_truth: const false`) and `turing approval preview` (`main.rs:658–704`), whose output string carries the full approval card *plus* `writes_micro_truth=false`. **WEB** cross-check: this is the propose/execute separation with approval-before-side-effects that operator-safety literature converges on ([StackAI — HITL approval workflows](https://www.stackai.com/insights/human-in-the-loop-ai-agents-how-to-design-approval-workflows-for-safe-and-scalable-automation), [Maxim — manual approval vs autonomous execution](https://www.getmaxim.ai/articles/manual-approval-vs-autonomous-tool-execution-designing-safe-ai-agent-loops/), [Microsoft — runtime authorization for agents](https://techcommunity.microsoft.com/blog/microsoft-security-blog/authorization-and-governance-for-ai-agents-runtime-authorization-beyond-identity/4509161)); the console's default-deny shape (every mutation verb gates on a route the console itself cannot satisfy) is the pattern's strictest form.
3. **Authorization**: the `authorization` lane (`lib.rs:260–264`: "latest authorization event; permission, not completion") + `authorization_head` + signing routes (`production_approval_route_allowed` rejects `in-memory-test` and `local-file-dev`; verified EXECUTED via `audit_operator_agent.py` PASS).
4. **Sovereign acceptance**: `accepted_head` only ("latest sovereign accept event from replay-derived head movement"), plus the five permitted lifecycle labels from `panorama.py`/`refs.md App C §C.1.1` — with the copy-law lint mechanically banning acceptance vocabulary elsewhere.

## 3. Recommendation

**Adopt HCI-A projection-only by ADR now; rescue by archive-then-rebase this week (it is conflict-free today, EXECUTED-verified); keep the 16-verb surface as schema-pinned intent-previews; build the projection-integrity audit as four machine checks (shadow rebuild, independent head derivation, provenance-manifest closure, render fidelity); prove no-write with layered static gates (dependency-direction + TapeReader capability type + clippy disallowed-methods + self-testing grep gate) closed by two dynamic tests (head conservation, read-only-FS matrix); stay plain-CLI with a `--json` mode; defer HCI-B behind three written preconditions; forbid HCI-C.**

Rationale against the program's goals:

- **Long-running autonomy:** the owner must be able to *watch* multi-day autonomous runs without becoming a shadow authority or an untaped mutation path. A projection-only console with a schema-constant `can_write_truth: false` is the only HCI that adds observability while adding zero authority surface — which is why G7 is worded "operator visibility without a shadow authority".
- **Replayability (Art. 0.2):** every recommendation above reduces to one invariant — displayed bytes are a pure function of tape bytes. The JCS `snapshot_hash` already on disk makes that invariant *checkable by equality*; the provenance manifest makes it checkable *per field*; the independent reference reader makes the check non-self-referential (the same meta-lesson as audit F1: never let the implementation certify itself).
- **Sandboxed execution:** the console executes nothing and mutates nothing, so it needs no runsc envelope; the read-only-FS dynamic test gives a physical guarantee stronger than policy. The one filesystem side effect (bundle scratch dir in `$TMPDIR`) is named and bounded.
- **Goodhart shielding (Art. III.4):** the console is owner-facing, not worker-facing — but the audit must still assert no worker-visible artifact consumes `operator_view_snapshot.v1` (the snapshot legitimately shows heads and lane states that worker-safe packets must not), so the provenance audit gains one leakage check: grep the worker-packet builders for the snapshot schema id, expect zero hits.
- **Observability:** structured verdict JSONs for every gate (house NFR §6); the console itself *is* the observability deliverable, and its evidence bundle pattern (`evidence_package.json` with per-command sha256s) already conforms.
- **Modularity:** `turing-projection` stays a leaf crate with no writer dependency; the console consumes the same snapshot contract as `turing-viewd`, preventing a second view-truth; the closed verb set is the frozen interface future HCI-B implements *behind* the authority kernel rather than beside it.
- **Cost:** M6 is the lowest-priority module, and this plan keeps it that way: the rescue is ~half a day (apply-check already CLEAN); the gates are ~2–3 agent-days total; everything else is deferred. The only non-deferrable item is the archive+rebase, because its cost is near-zero *today* and grows with every commit to main.

**HCI-B deferral preconditions (write these into the ADR verbatim):** HCI-B (actual typed-command *submission* into the MicroTape path) may be proposed only when ALL of: (1) the authority kernel / canonical-writer question is closed by M1 (single designated writer, cross-impl byte-equality gate green in CI, `--require-authorization-head` passing on a real run); (2) the M2 Turing-completeness witness is done (gates TC-01..TC-10 PASS, independently audited); (3) the M5 external-audit machinery is live (ClosureCertificate.v1 issuable by a custody-separated cross-family verifier), so that a command console lands in a world where independent verification already exists. Even then, HCI-B requires its own ADR plus owner sign-off, and its commands enter the tape only through the same daemon/authorization path as any other proposer — never a private path. **HCI-C remains forbidden** this program increment (Intent §7).

## 4. Pitfalls and mitigations

1. **The work evaporates before the ADR lands.** The diff has sat uncommitted since 2026-06-29 on a cloud VM; one careless `git checkout .` destroys 1,666 lines. *Mitigation:* archive (patch + untracked tarball + sha256 manifest) as the literal first implementation action, before any rebase attempt; the EXECUTED patch export in this research (sha256 `ca61116816ce7c3b661f3594fdf91b9d2ee35886aa4dfe38c5b7750e262182af`) doubles as an integrity reference.
2. **Committing the console re-front-runs the ADR.** F6's complaint is sequencing, not code quality. *Mitigation:* strict order — ADR-M6-001 text accepted first (plan artifact), then the rescue commit whose message cites the ADR; the commit lands on a feature branch, and merge to main is gated on the M6 audit gates being green.
3. **The verb names oversell.** APPROVE_CAPSULE/DISPATCH_WORKER *read* like a control console; a future agent (or the owner at 2 a.m.) could claim "TuringOS has an operator command console." *Mitigation:* ADR-M6-003 names them intent-previews; the copy-law lint already bans completion vocabulary; add one lint rule banning the phrase "command console" outside quoted HCI-B deferral text; the `writes_truth: const false` schema constant makes the honest state machine-checkable.
4. **Capability leak: `Append` in CLI scope.** The write-capable type is imported where only reads happen (`main.rs:2`); today's discipline is convention. *Mitigation:* the `TapeReader` split (§2.5-2) plus clippy `disallowed-methods` plus the grep gate; until `TapeReader` exists, the grep gate alone must ban `.append(`/`.stage(`/`AppendRequest` in the operator modules (EXECUTED-verified zero hits today — pin that).
5. **Stale evidence after rebase.** `evidence_package.json` pins `base_sha: 6b9daad`; after rebasing, its baseline PASS records describe a tree that no longer exists, and the audit meta-lesson (F1) is precisely about evidence that quietly stops matching reality. *Mitigation:* keep the original bundle as an immutable FIXTURE-labeled archive; regenerate the evidence package at the new base as part of the rescue atom; add `CLAIM_BOUNDARY.json` to the evidence root stating IMPLEMENTER_ADDRESSED ceiling and FIXTURE provenance of demo-tape outputs.
6. **Demo/real confusion.** Bare `turing status` renders the *demo* replay; the text renderer shows `source_kind=deterministic_replay` but not `micro_repo=qualification_demo_micro_tape`. An operator glancing at a heartbeat could mistake demo heads for project heads. *Mitigation:* render fidelity fix in the rescue commit — include `micro_repo` in both text renderers; optionally require an explicit `--demo` flag long-term; the render-fidelity audit (§2.4-4) then pins it.
7. **Static analysis false confidence.** Clippy misses higher-order calls and `#[allow]` overrides (WEB, issue #8849); grep gates miss dynamic dispatch through helper crates. *Mitigation:* the gates are layered by design, and the two *dynamic* tests (head conservation + read-only FS) are the load-bearing floor: a write that survives all static gates still fails EACCES/conservation. Never report the static gates alone as "zero head-moving paths PASS" — the KPI requires static AND dynamic.
8. **Two view-truths (console vs viewd).** `turing-viewd` already builds/writes projection snapshots via RPC; the console builds `operator_view_snapshot.v1` in-process. If their derivations drift, the system has two "views of truth" — a soft F2-style fragmentation. *Mitigation:* both must consume `turing-projection`'s builder (viewd already lives in-workspace), and the shadow-rebuild audit should also compare console-built vs viewd-built snapshots for the same tape.
9. **Console output leaking into worker context.** Snapshot fields (heads, lane meanings, next_sovereign_action) are owner-eyes information; if an orchestrating agent pastes console output into a worker prompt, Goodhart shielding erodes. *Mitigation:* one grep in the worker-safe packet builder for `operator_view_snapshot` (expect zero); a one-line warning banner in `panoview` output ("owner projection — not worker-safe material") enforced by the render-fidelity check.
10. **Scope creep toward HCI-B "just one small write".** The single most likely drift: someone wires APPROVE_CANDIDATE to the daemon "since the plumbing is right there." *Mitigation:* the deferral preconditions are written into the ADR as blocking; the no-write gates fail CI the moment a daemon-mutation RPC name (`approval.authorize_atom`, `capsule.approve`, `event.append_preserve`, `grant.authorize`) appears in the operator modules — add those strings to the grep gate ban list now.

## 6. ADR-ready decision records (MADR-style)

**ADR-M6-001 — Adopt HCI-A (projection-only) as the sole HCI route for this program increment; defer HCI-B with written preconditions; forbid HCI-C.** *Context:* the repo's own retrospective (`turing/docs/handoff/TURINGOS_PROJECT_RETROSPECTIVE_AND_EXTERNAL_AUDIT_PROMPT_20260702.md:395–434`) defines three routes and recommends HCI-A; audit F6 found the route undecided while an HCI-B-shaped surface was already built; Project Intent G7 requires an accepted HCI-A ADR and §7 forbids HCI-B-beyond-previews and HCI-C. *Decision:* the console is a projection and preview adapter, never an authority: `can_write_truth`/`writes_truth` remain schema constants `false`; HCI-B may be re-proposed only after (1) M1 closes the canonical-writer/authorization question with a real `--require-authorization-head` PASS, (2) the M2 TC witness is independently audited, and (3) M5's external ClosureCertificate machinery is live — and then only via a new owner-approved ADR routing commands through the same daemon path as every proposer; HCI-C is forbidden this increment. *Consequences:* the owner gets observability with zero new authority surface; drift toward a command console becomes a CI failure rather than a judgment call; the cost is that genuine operator actions still require the existing non-console paths until HCI-B's preconditions are met.

**ADR-M6-002 — Rescue the uncommitted console work by archive-then-rebase onto the active HEAD; merge gated on the M6 gates.** *Context:* 1,666 diff lines + 863 untracked Python lines + schemas/docs/evidence sit uncommitted in a second clone at base `6b9daad`, 14 commits behind active HEAD `bed75977`; EXECUTED verification (2026-07-02) shows the 14 intervening commits touch zero overlapping files and `git apply --check` is CLEAN at `bed75977` (patch sha256 `ca61116816ce7c3b661f3594fdf91b9d2ee35886aa4dfe38c5b7750e262182af`). *Decision:* first archive (patch + untracked tarball + sha256 manifest + CLAIM_BOUNDARY.json) into the active repo's evidence tree, then apply onto a new branch `hci/operator-console-v1-rebased` at `bed75977`, re-run the full Rust+Python test set, commit citing this ADR, push; merge to main only when the ADR-M6-004/005 gates are green in CI; the old clone is then retired from duty (kept or deleted per owner preference, never edited). *Consequences:* loss risk drops to zero the same day; the conflict-free window is used while it exists; the stale `base_sha` in the original evidence package is preserved as a labeled FIXTURE archive and regenerated at the new base.

**ADR-M6-003 — Keep the closed 16-verb typed-command surface as schema-pinned intent-previews under HCI-A (not command submission, not deleted).** *Context:* the built surface is verb-wise HCI-B-shaped (PROPOSE/APPROVE/DISPATCH) but behavior-wise projection + dry-run preview — verified on disk: `typed_command.v1` pins `writes_truth: const false` and `dry_run_default: true`; mutation verbs terminate at `approval_required`/`human_signature_required` preview text; the deterministic agent router refuses shell-shaped utterances; Intent §7 explicitly grandfathers "dry-run previews already built". *Decision:* retain all 16 verbs as the frozen *specification* of a future HCI-B, rendered only as previews; no verb may gain an execution path under this ADR; the copy law lint additionally bans the unqualified phrase "command console"; renderers must consume `operator_view_snapshot.v1` and may format but never derive. *Consequences:* ~half the rescued work (verb specs, boundary tests, journey matrix) stays alive and tested instead of deleted-and-rewritten later; the residual risk that the verbs oversell is carried by machine checks (schema constants, copy lint, no-write gates) rather than prose.

**ADR-M6-004 — Projection-integrity audit = shadow rebuild + independent head derivation + provenance-manifest closure + render fidelity, executed by a reference reader that never imports the projection crate.** *Context:* G7 demands "100% of console-displayed values replayable from tape (automated audit)"; CQRS practice establishes rebuildable read models and shadow-projection validation ([Event-Driven.io](https://event-driven.io/en/projections_and_read_models_in_event_driven_architecture/), [Azure event-sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing), [Mageed](https://www.ashrafmageed.com/cqrs-eventsourcing-and-the-cost-of-tooling-constraints/)); the snapshot already self-commits via a JCS `snapshot_hash` (`turing-projection/src/lib.rs:303–319`); the house precedent for independent auditors is `audit_micro_tape_decision_dag.py`; hash-equality alone cannot catch a deterministic-but-wrong builder, and unreviewed new fields are the classic leak. *Decision:* implement `tools/hci/audit_projection_integrity.py` with the four checks plus the worker-leakage grep, emitting `hci_projection_integrity_verdict.v1` JSON with NOT_RUN==FAIL; a checked-in provenance manifest maps every snapshot JSON pointer to its tape derivation and unclassified fields fail the audit; a `--json` output mode makes displayed bytes equal schema bytes. *Consequences:* "replayable from tape" becomes a per-field mechanical property; adding a console field now requires declaring its derivation, which is exactly the friction Art. 0.2 wants; cost is one ~300-line auditor plus a manifest file.

**ADR-M6-005 — No-write enforcement is layered: dependency-direction check + read-only `TapeReader` capability type + clippy `disallowed-methods`/`disallowed-types` + self-testing grep gate, with dynamic head-conservation and read-only-filesystem tests as the floor.** *Context:* G7 requires "zero head-moving UI paths (static + dynamic check)"; verified today: `turing-projection` has no tape-writer dependency, the console calls only `head_set_guarded()` (SG-18 read), and a write-call grep over both surfaces returns zero hits — but `turing-cli` imports the write-capable `Append` type, clippy's lint cannot see higher-order calls ([rust-clippy #8849](https://github.com/rust-lang/rust-clippy/issues/8849)) and can be locally `#[allow]`-ed, and the existing dynamic tests assert heads are displayed, not conserved. *Decision:* add (1) a `cargo metadata` gate freezing turing-projection's writer-free dependency set, (2) a `TapeReader` read-only handle in `turing-git-tape` (coordinated with M1) so operator code never holds `Append`, (3) workspace `clippy.toml` disallowed entries for `Append::append/stage/append_with_contention`, `StagedAppend::commit/re_mint_and_commit`, `AppendRequest` enforced with `-D` in CI, (4) `gate_hci_no_write.sh` in the proven self-testing gate_g10 style (also banning daemon mutation RPC names and the clippy-allow attribute), and (5) two dynamic tests: every console command run against a fixture tape with all three refs asserted byte-identical before/after, and the same matrix run on a `chmod -R a-w` tape where any latent write fails EACCES. *Consequences:* no single mechanism is trusted alone; the static gates catch drift at review time and the dynamic tests make a hidden write physically non-executable; reporting discipline: "zero head-moving paths" may only be claimed with static AND dynamic gates green, at IMPLEMENTER_ADDRESSED ceiling.

**ADR-M6-006 — Console presentation stays plain CLI (stdin/stdout) with a verbatim `--json` snapshot mode; TUI deferred; web forbidden this increment.** *Context:* the existing console is a plain text loop, all 16 CLI gate tests work by argv+stdout assertion; CLI-guidelines practice favors machine-readable, pipeable, stateless output for audit tooling ([clig.dev](https://clig.dev/)); a ratatui TUI is testable but brittle (TestBackend/insta snapshots, no color assertions, PTY gaps — [ratatui testing recipe](https://ratatui.rs/recipes/testing/snapshots/)) and adds console-local derived state the render-fidelity audit cannot easily see; a web console adds credential and served-endpoint surface with HCI-C gravity for zero G7 benefit to a single operator; the house already treats rich UI as optional (`panorama.py` renders without `textual`). *Decision:* keep plain CLI; add `--json` printing the `operator_view_snapshot.v1` bytes verbatim; text renderers must also print `micro_repo` so demo vs real tapes are unmistakable; any future TUI must be a formatter over the same snapshot contract and requires no new ADR only if it derives nothing; any web surface requires a new owner-approved ADR and is out of scope now. *Consequences:* audit property "displayed == schema bytes" is trivial in JSON mode; agents and shell pipelines consume the console directly; the operator experience stays spartan — an accepted cost for the lowest-priority module.
